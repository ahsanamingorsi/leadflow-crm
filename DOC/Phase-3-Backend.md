# Phase 3: Lead intake and routing backend

Implemented in the existing .NET MVC Web API with SQL Server and EF Core. It reuses the current workspace permissions, CRM contacts, activity history and audit log.

## Database

From `Backend/leadflow-crm.API`, apply migrations with:

```powershell
dotnet ef database update -- --environment Development
```

Migration `20261018082827_LeadRoutingPhaseThree` adds leads, durable intake, assignment history, employee availability, assignment settings, in-app notifications and the email-delivery queue. It also creates a hashed public-intake-key column, an optional user notification email, makes CRM activity actors nullable for system events, and backfills default settings, availability and Phase 3 permissions for existing workspaces. New workspaces and invited users get their defaults during setup.

## Lead lifecycle

Manual and public intake accept an `Idempotency-Key`. A workspace-scoped hash prevents duplicate intake records. If an available employee is below the configured open-lead limit, intake creates or matches a contact and assigns the lead immediately. A public intake with no eligible owner remains durably queued for the background worker. If an email/phone match points to multiple contacts, the intake enters `NeedsContactReview` for an authorized manager to resolve.

Assignment uses a round-robin cursor across eligible employees. Availability changes reassign unacknowledged leads where possible. Each lead has a persisted acknowledgement deadline; a hosted worker processes overdue leads and queued intake after restarts. Leads with no remaining eligible owner are marked for manager attention and retried. Adding a contact or opportunity note for a lead's current owner records that action and acknowledges the lead.

The public intake key is generated by the authenticated key-rotation endpoint and shown once; only its hash is stored. Rotating it invalidates the previous key. Public intake is rate-limited to 10 requests per minute per source IP. In-app assignment notifications are always recorded. Escalation emails are queued and retried up to three times when SMTP is configured.

## Endpoint map

| Resource | Operations |
| --- | --- |
| `/api/leads/intake` | POST manual lead intake (`Idempotency-Key`) |
| `/api/leads` | GET paginated leads; filter by owner, status, source, dates and search |
| `/api/leads/{id}` | GET lead detail |
| `/api/leads/{id}/acknowledge` | POST owner acknowledgement using `rowVersion` |
| `/api/leads/{id}/reassign` | PUT manager reassignment with reason and `rowVersion` |
| `/api/leads/{id}/close` | POST close a lead |
| `/api/leads/{id}/assignments` | GET assignment history |
| `/api/leads/recovery` | GET overdue, repeatedly escalated or idle leads for managers |
| `/api/leads/intakes` | GET queued and contact-review intakes |
| `/api/leads/intakes/{id}/retry` | POST retry an intake, optionally selecting the matched contact |
| `/api/workspace/assignment/settings` | GET/PUT routing limits, acknowledgement and escalation timing/fallbacks |
| `/api/workspace/assignment/public-intake-key` | POST rotate the public website intake key (returns key once) |
| `/api/workspace/assignment/availability` | GET availability and open-lead counts |
| `/api/workspace/assignment/availability/me` | PUT own availability |
| `/api/workspace/assignment/availability/{userId}` | PUT an employee's availability as a manager |
| `/api/workspace/assignment/my-notification-email` | PUT optional escalation email destination |
| `/api/workspace/assignment/my-notifications` | GET notifications; POST `/{id}/read` to mark read |
| `/api/workspace/assignment/email-delivery` | GET queued/sent/failed escalation email status |
| `/api/workspace/assignment/email-delivery/{id}/retry` | POST retry a failed email |
| `/api/public/leads` | POST website intake with `X-Leadflow-Intake-Key` and `Idempotency-Key` |

Scalar is available at `https://localhost:7178/scalar/` when the API is running with the HTTPS launch profile. Authenticated writes continue to require the session cookies and antiforgery token described in [Phase 2](Phase-2-Backend.md).

## SMTP configuration

Set these environment variables for the API process; do not commit credentials:

```powershell
$env:Notifications__Smtp__Host = "smtp.example.com"
$env:Notifications__Smtp__Port = "587"
$env:Notifications__Smtp__FromAddress = "crm@example.com"
$env:Notifications__Smtp__EnableSsl = "true"
$env:Notifications__Smtp__Username = "smtp-user"
$env:Notifications__Smtp__Password = "smtp-password"
```

If host or from-address is missing, email records stay queued and can be inspected from the email-delivery endpoint. A provider-specific sender can replace the SMTP adapter without changing lead assignment behavior.

## Verification and scope

`Backend/tests/phase3_smoke.mjs` runs focused checks against an already running API and SQL Server. Run it from the repository root with Node.js:

```powershell
$env:NODE_TLS_REJECT_UNAUTHORIZED = "0"
node Backend/tests/phase3_smoke.mjs
```

The smoke check creates an isolated uniquely named workspace and removes that workspace in a `finally` cleanup. It covers owner permissions/defaults, settings, availability, manual intake, idempotency, lead listing/detail, assignment history, acknowledgement, in-app notification, public key acceptance and invalid-key rejection.

Email delivery requires SMTP credentials to be supplied by the operator. Twilio WhatsApp message intake/delivery and Angular screens remain for later phases; Phase 3 provides the routing and activity seams only.
